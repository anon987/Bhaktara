# Media Pipeline, Delivery and Search

> Decisions: D-001, D-004, D-012, D-031, D-032. D-035.
> Tags: **[Decided]** · **[Rec default — adjustable]**

## Part A — Media

### A1. Hosting [Decided: D-031]

- All public media (audio, ringtones, wallpapers, thumbnails, status videos, banner images, deity/Mandir art) is stored in **Cloudflare R2**.
- Media is served through the **Cloudflare CDN** on a custom domain, e.g. `media.bhaktara.<tld>`.
- Firebase Storage is not used for public media.

### A2. Asset keys, not URLs [Decided]

Firestore stores asset keys and metadata. The client builds each URL as:

```text
url = mediaBaseUrl + "/" + key
```

`mediaBaseUrl` comes from `appConfig` / Remote Config. This lets the CDN domain change without data migration.

**Key format [Rec default]:** content-addressed and immutable.

```text
{type}/{contentId}/{variant}.{hash8}.{ext}
e.g. wallpaper/wp_0142/mobile.3f9a1c2e.webp
```

- A changed file produces a new key.
- Caches never need purging.
- `Cache-Control: public, max-age=31536000, immutable`

### A3. Variants per type [Rec default — matches doc 12 §6]

| Type | Variants |
|---|---|
| Audio | `stream` (AAC/MP3, 96–128 kbps), `thumb` |
| Ringtone | `file` (MP3), `thumb` |
| Wallpaper | `thumb` (~300 px WebP), `mobile` (1080×2400 WebP), `full` (master, used for "Save" and "Set") |
| Status video | `video720` (H.264 MP4), `poster` (WebP), `thumb` |
| Banner / deity / Mandir art | `mobile` (WebP), `thumb` |

**Metadata stored per variant:** `key`, `bytes`, plus as applicable `width`, `height`, `durationSeconds`, `bitrate`, `mime`.

### A4. Upload and processing flow [Rec default]

Both flows use the same **media processor** module (ffmpeg + image library), so the output is identical either way.

**Admin upload (single item)**
1. The CMS requests an upload slot.
2. A Cloud Function checks the admin custom claim and returns a presigned R2 PUT URL for a `staging/` prefix.
3. The admin browser uploads the original directly to R2.
4. The CMS calls `processMedia`, which runs on Cloud Run because ffmpeg needs a container. It:
   - validates type, size and duration
   - produces the variants
   - writes them under final keys
   - updates the content doc
   - deletes the staging file

**Seed/bulk import (doc 18)**
- The import script runs the media processor locally (or in CI) against the asset folder.
- It uploads the variants with admin credentials held on the operator machine, never in the app.
- It then writes Firestore docs.

**Secrets**
- The R2 access keys live only in Cloud Functions/Cloud Run secret storage and on the operator's machine.
- They never appear in the mobile app or the admin web bundle.

### A5. Client delivery rules [Decided principles]

- Lists and rails load `thumb` only.
- `mobile` or `full` is loaded only on detail or save.
- Audio streams from `stream`, with progressive download and HTTP range requests.
- Status videos load `poster` first. The video loads only on tap, never autoplaying in lists.
- An image cache with a disk limit is used.
- Wallpapers and ringtones are saved to the device from `full`/`file` on explicit user action (the "Save/Set" feature — doc 02).

### A6. Access control

- **V1:** all media is public-read through the CDN. There is no premium content in V1.
- **Future premium:** premium keys go under a `premium/` prefix served through a Cloudflare Worker that validates a short-lived signed token issued by a Cloud Function after an entitlement check.
- The schema already carries `isPremium` so this can be added without migration.

### A7. Cost notes

- R2 has no egress fee. Storage and operations are billed.
- Firestore is used only for metadata reads, which is why the home feed is precomputed (doc 05).
- **Monitor:** R2 storage GB, Class A/B operations, CDN cache hit ratio (target > 90%), Firestore reads per DAU.

## Part B — Search

### B1. Approach [Decided: D-032]

Each published content doc carries `searchTokens: string[]`. The array is generated by a Cloud Function on publish or update and is never written by the client or by hand.

**Token sources**
- `title.hi` and `title.en`
- deity localized names and aliases
- category names
- tags, including operator-added transliterations

**Normalization [Rec default]**
- lowercase
- strip punctuation
- Devanagari: remove nukta and normalize chandrabindu to anusvara
- Latin: collapse doubled vowels (`aa→a`, `ee→i`, `oo→u`) and common phonetic swaps (`w↔v`, `sh↔s` variants), so "hanumaan" and "hanuman" normalize to the same token

**Prefixes**
- For type-ahead, store edge prefixes of each normalized word, from 2 to 10 characters.

**Size guard**
- Cap at about 200 tokens per doc.

### B2. Query

1. Normalize the query with the same rules.
2. Pick the longest token and run `where('searchTokens', 'array-contains', token)` with `status == 'PUBLISHED'` (schema v2) and a limit (paginated).
3. Filter the remaining query words on the client.
4. Optional type filter is applied in the same query (composite index).

### B3. Known limitations (accepted with D-032)

- No typo tolerance beyond the normalization rules.
- Weak relevance ranking. Results are sorted by popularity score, not by match quality.
- Multi-word queries only match on one server-side token.
- Transliteration quality depends on the operator adding good tags.

### B4. Rejected alternative (D-035)

An on-device search index (a JSON file on the CDN plus fuzzy search in the app) was considered and rejected for V1. Revisit it if zero-result rates or search complaints are high.

### B5. Search analytics

- Log `content_search` with the normalized query and result count.
- Log zero-result queries so the operator can add missing tags. This review is part of the weekly cadence in doc 12 §8.

## Implementation checkpoint — 2026-10-04

The local Firebase adapter now implements bounded search-token queries with popularity/document-ID cursors and query-bound cursor validation. Text search filters additional words and deity within each returned page because Firestore permits only one array-contains clause. Without text, deity filtering runs server-side. Empty filtered pages retain their continuation cursor. Seed-generated tokens share normalization with queries; production publishing is still pending. The root `firestore.indexes.json` contains required indexes. Production CDN delivery/media remain unimplemented.

## Implementation checkpoint — R2 media (2026-10-04)

Client and operator sides of Part A are implemented; no Cloudflare resources are provisioned yet. Shared key validation, the doc 06 `MediaVariant` schema and the URL join live in `src/domain/media.ts`. Presigned CMS uploads, `processMedia` on Cloud Run, audio playback and native save remain pending. Runbook: `docs/MEDIA_R2.md`.
