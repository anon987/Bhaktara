# Content Operations and Publishing

> Operating model: **one operator** (the product owner) creates, checks and publishes all content using AI tools (D-001, D-010).
> There is no second reviewer. This document replaces that missing reviewer with mandatory checklists and provenance records.
> Tags: **[Decided]** · **[Rec default — adjustable]** · **[Pending]**

## 1. Content source

- All vocal audio is AI-generated, including mantra, chalisa and aarti (D-010).
- Wallpapers, ringtone music and status videos are produced with AI and external tools.
- AI is an internal production tool only. The app has no user-facing AI generation.
- AI use is disclosed only on the app's About/Credits page (D-013). Suggested copy:
  "Bhaktara ke kuch audio aur visuals AI tools ki sahayata se banaye gaye hain."
  The final wording is the product owner's choice.

## 2. Known risks of this model (accepted by the product owner)

| Risk | Mitigation in this document |
|---|---|
| AI mispronounces Sanskrit (anuswar, visarga, conjuncts) | Canonical source text (§3), listen-through check against the text (§5) |
| AI tool plan may not grant commercial rights | License record for every tool and plan used (§4) |
| AI output may have weak copyright protection, so it can be copied by others | Accepted. The audio library is not treated as a moat. |
| No second reviewer | Mandatory checklist before any item can be published (§5) |
| No in-app error reporting in V1 (D-014) | Monitor Play Store reviews weekly for content complaints (§8) |

## 3. Canonical source text (mandatory for sacred text audio)

Every mantra, chalisa and aarti item must record:
- the exact Devanagari text used as the generation input, stored internally and not shown in the app in V1 (D-011)
- the source of that text: a named public-domain edition or tradition reference

**Rules:**
- Never generate sacred text audio from a prompt alone ("Hanuman Chalisa gao"). The text must be supplied verbatim.
- Before publishing, compare the generated audio against the stored text line by line.

## 4. AI tool license record

Keep a record for every AI tool used in production:
- tool name
- plan or tier
- date
- the commercial-use clause as it read on that date (screenshot or saved copy)

Each content item stores the tool that produced it. Schema fields are pending (P-04).

## 5. Pre-publish checklist (single operator)

An item cannot be marked ready unless every applicable box is checked. The CMS enforces this (see `09_ADMIN_CMS_PRD.md`).

**All items**
- [ ] Title correct in Hindi and English, spelling checked
- [ ] Deity, category and tags correct
- [ ] Thumbnail readable at small size
- [ ] AI tool and plan recorded (§4)
- [ ] Save/share policy set

**Sacred text audio (mantra, chalisa, aarti)**
- [ ] Canonical source text stored (§3)
- [ ] Full listen-through against the text: no skipped, added or garbled lines
- [ ] Sanskrit sounds checked: anuswar, visarga, conjuncts
- [ ] No mid-word cuts, clipping or artifacts

**Bhajan audio**
- [ ] Full listen-through
- [ ] No unintended lyrics or artifacts

**Visuals (wallpapers, status video frames, thumbnails)**
- [ ] Iconography correct: vahana, ayudh, attributes, number of arms, colour conventions for the deity
- [ ] No distorted hands, faces or extra limbs
- [ ] No disrespectful framing, cropping or overlays

**Ringtones**
- [ ] Clean start and end, no clipped syllable
- [ ] Loud enough on a phone speaker

## 6. Production standards [Rec default — adjustable]

| Asset | Spec |
|---|---|
| **Audio (bhajan/aarti/mantra/chalisa)** | AAC or MP3, mono or stereo, 96–128 kbps, loudness-normalized (target about −16 LUFS), trimmed silence |
| **Ringtone** | 20–30 s, MP3, normalized, designed for looping or a clean end |
| **Wallpaper** | Master at least 1440×3200. Variants: thumbnail (about 300 px wide, WebP), mobile (1080×2400, WebP/JPEG), full (master, used for "Save") |
| **Status video** | 9:16, 15–30 s, H.264 MP4, 720p primary, target under 6 MB, plus a poster frame |
| **Thumbnails** | WebP, compressed, legible at card size |

Renditions are generated by the upload pipeline. They are not produced manually.

## 7. Metadata taxonomy

Every item must have:
- content type
- deity (canonical ID)
- category
- language
- tags (Hindi, English and common transliterations — this matters for search)
- festival relevance
- featured flag
- premium flag (future)

## 8. Operating cadence (single operator)

| Cadence | Task |
|---|---|
| **Daily** | Check the Home schedule. Check Crashlytics for new crash spikes. |
| **Weekly** | Publish new content in batches. Read Play Store reviews for content-accuracy complaints and fix affected items immediately. Plan next week's challenges. |
| **Monthly** | Prepare festival content 4–6 weeks ahead of each festival. |

## 9. Seasonal content

Prepare collections, banners and status videos ahead of:
- Navratri, Dussehra, Diwali, Govardhan Puja, Bhai Dooj
- Makar Sankranti, Mahashivratri, Holi
- Ram Navami, Hanuman Jayanti, Janmashtami, Ganesh Chaturthi
- selected regional festivals

Festival dates are data-driven from the festival manager and are never hard-coded.

## 10. Collections (editorial)

Morning Bhakti · Evening Aarti · Shiva Bhakti · Krishna Bhakti · Hanuman Bhakti · Devi Bhakti · Navratri Special · Diwali Special · Daily Mantra · Wallpapers of the Week · Devotional Status

## 11. Workflow states (D-036)

`DRAFT → READY → SCHEDULED → PUBLISHED → ARCHIVED`

- An item can move to READY only when every applicable checklist box in §5 is ticked. The CMS enforces this.
- A PUBLISHED item can be moved back to DRAFT to unpublish it for a fix.
